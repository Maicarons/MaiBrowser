# v0.2 升级研究

> 结论先行：0.2 的主线不应该是“再堆几个设置项”，而是把 0.1 已经露出轮廓、但还没有闭环的**浏览器基础能力**补完：下载、站点权限与证书错误、Android 端对齐、油猴脚本的资源加载，以及可重复的发布工程。Android DuckDB 和多窗口建议放到 0.3，除非上游 CEF 绑定在同一周期内提供了稳定的下载/权限/请求上下文接口。

## 0.1 的基线

0.1.0 已经完成的事情很扎实：共享 UI、CEF/系统 WebView 双引擎、标签页与会话、历史、书签、主题、i18n、DuckDB、油猴脚本 v1、Windows NSIS 和 Android APK。它已经是一个能打开、能浏览、能保存数据的浏览器，而不是界面原型。

但代码审计和 0.1 的已知限制指向同一组缺口：

| 缺口 | 0.1 现状 | 用户能感知到的后果 |
| --- | --- | --- |
| 下载 | `downloads` 表和下载页存在，但没有引擎下载事件 | 点击下载链接没有可靠反馈，下载页只能管理旧记录 |
| 站点权限 | DuckDB 有 `permissions` 表，但没有请求 UI 和平台回调 | 摄像头、麦克风、定位、文件选择等能力不可用或直接失败 |
| 证书错误 | 只有通用加载错误 | 用户看不到“证书有问题”的明确解释，也没有安全的选择 |
| 隐私标签 | 只跳过历史与会话写入 | Cookie 仍然共享，和“隐私浏览”的用户预期不一致 |
| Android 对齐 | JSON 快照、无文件导入导出、无下载写入 | 桌面端能做的事，手机上缺一截 |
| 油猴资源 | 解析了 `@require` / `@resource`，注入时没有加载 | 依赖外部库的脚本会在运行时报错 |
| 发布 | 安装包未签名，APK 为 debug 签名，版本号不一致 | SmartScreen 警告、无法上架、升级链路不可信 |

这些问题有一个共同点：它们都卡在**平台能力层**，而不是 UI 层。继续在设置页里加开关，收益会越来越小；0.2 应该把平台层打通。

## 0.2 的目标

0.2 完成后，用户应该能：

1. 从网页下载文件，看到进度，暂停/继续/取消，打开文件或所在目录，重启后记录还在。
2. 在网站请求摄像头、麦克风、定位或文件时看到明确的权限提示，并能记住“允许/阻止”。
3. 遇到证书错误时看到一个清晰的错误页，默认回到安全页面，而不是只看到“加载失败”。
4. 在 Android 上完成文件选择、下载、书签导入/导出，并保持和桌面端一致的数据语义。
5. 安装依赖 `@require` / `@resource` 的常见油猴脚本，`GM_download` 真正可用。
6. 从 Releases 下载到带校验和、版本号一致的安装包/APK；维护者能用 CI 重复构建。

### 不在 0.2 范围内

- 云账号、书签/密码同步、遥测。
- 广告拦截、密码管理器、内置 AI 功能。
- 完整的多窗口/标签撕裂。
- Android DuckDB NDK（见下文，建议 0.3）。
- 自动静默更新（没有代码签名之前不做）。

## 优先级与工作量

按“用户价值 × 阻塞程度 ÷ 风险”排序。工作量按一名熟悉该代码库的工程师估算，单位为人周，包含测试与文档，不包含上游 review 等待。

| 优先级 | 工作流 | 价值 | 估算 | 依赖 |
| --- | --- | --- | --- | --- |
| P0 | 下载管理器（桌面 + Android） | 浏览器基础能力 | 2–3 | CEF 绑定、Android WebView 服务 |
| P0 | 站点权限与证书错误 | 安全与可用性 | 2 | CEF 权限回调、Android WebChromeClient |
| P0 | Android 端对齐 | 两端体验一致 | 2 | Android 原生模块 |
| P1 | 油猴 `@require` / `@resource` / `GM_download` | 脚本生态 | 1.5 | 下载管理器、存储 |
| P1 | 发布工程与版本一致性 | 可分发、可维护 | 1.5 | GitHub Actions、签名材料 |
| P1 | Android 状态快照可靠性 | 防止数据损坏 | 1 | 无 |
| P2 | 隐私标签的完整 Cookie 隔离 | 隐私承诺 | 1–2 | CEF 请求上下文 |
| P2 | 多窗口 | 重度用户 | 2 | 平台窗口模型 |

P0 + P1 合计约 8–10 人周。若把隐私隔离和多窗口都塞进 0.2，会变成 12–14 人周，且关键路径受上游 CEF 绑定影响，不建议。

## 工作流 A：下载管理器

### 桌面端

当前 `@lynx-js/cef-webview@0.0.31` 的 JavaScript API 只暴露 `initialize()` 和 `<webview>` 的 `load`、`error`、`locationchange`、`message`、`openwindow` 事件，没有下载事件，也没有暂停/取消控制。`packages/ui/src/App.tsx` 里的 `gm:download` 分支目前只弹出一句“Download handler is not wired yet”。所以桌面端下载不是 UI 问题，而是绑定能力缺失。

可行路径，按优先级：

1. **向上游提交 CEF 绑定补丁**：在原生插件中实现 `CefDownloadHandler`，向 Lynx 暴露 `binddownload`（开始/进度/完成/失败）和 `download` 控制方法（暂停、继续、取消）。这是一条一次投入、长期受益的路。
2. **本地 fork 原生插件**：如果上游 review 周期不可控，在 `apps/desktop` 内维护一个最小 patch/fork，固定版本并在 `README`/`docs` 标注。代价是 CEF 升级时要重新对齐。
3. **兜底方案**：注入页面脚本拦截 `<a download>` 和常见文件扩展名链接，经主进程 `fetch` 写入磁盘。它不能覆盖表单 POST、`blob:`、PDF 查看器和跨域 Cookie 下载，只能作为临时降级，不能当作“下载已完成”。

建议把 1 作为 0.2 的默认方案，2 作为决策点后的备选，3 只用于无法升级绑定的过渡版本。

### Android 端

Android 侧的可行性比桌面好。`xelement-webview` 暴露了公开的 `ILynxWebViewService` 接口和 `LynxWebViewServiceProviderImpl.registerService()`；`ILynxWebViewService` 提供 `getWebView()`，可以在自定义 service 中给 `WebView` 设置 `DownloadListener`，再交给系统 `DownloadManager`。这条路径不需要修改 Sparkling 或 Lynx 的 AAR。

实现要点：

- 自定义 `MaiBrowserWebViewService` 包装默认 service，保留现有 `onPageFinished` / `onReceivedError` / `onMessageReceived` 回调。
- 下载交给 `DownloadManager`，用 `DownloadManager.Request` 设置目标目录、MIME、通知可见性；用 `ContentObserver` 或查询游标把进度回传给 Lynx。
- 需要 `WRITE_EXTERNAL_STORAGE` 的旧版本兼容策略：API 29 以下使用公共 Downloads 目录时需要权限，API 29+ 使用 scoped storage/MediaStore；0.2 至少要把 API 24–28 的行为定义清楚。
- 文件名冲突、Content-Disposition、HTTPS 证书错误、下载失败重试要有明确状态。

### 统一数据模型

现有 `DownloadRecord` 已有 `id`、`url`、`file_name`、`file_path`、`mime`、`total_bytes`、`received_bytes`、`state`、`started_at`、`finished_at`、`error`。0.2 建议扩展为：

```ts
type DownloadState =
  | 'queued'
  | 'downloading'
  | 'paused'
  | 'completed'
  | 'failed'
  | 'cancelled'
```

UI 的 `DownloadsPage` 增加暂停/继续/取消按钮，进度条使用 `received_bytes / total_bytes`；未知总大小时显示不确定进度。记录写入仍走现有的 `saveDownload` / `listDownloads` / `deleteDownload` 白名单，不新增绕过存储层的直接文件操作。

### 验收

- 从本地测试页下载 1 KB、10 MB、100 MB 文件，进度、完成状态、文件路径正确。
- 暂停后继续，字节数不回退；取消后文件不残留（或明确标记 `.part` 并在重启时清理）。
- 重启应用后，已完成的记录仍在，点击可打开文件/所在目录。
- Android 上下载完成通知可点击打开，API 24 与 API 34 各验证一次。

## 工作流 B：站点权限与证书错误

### 权限

现状：`packages/storage` 已有 `permissions` 表，但没有读写方法和 UI；桌面 CEF 绑定没有 permission handler；Android 没有自定义 `WebChromeClient`。

目标权限集合（0.2 只做这一组，避免范围膨胀）：

- 摄像头 / 麦克风（`getUserMedia`）
- 地理位置
- 通知
- 文件选择（`<input type=file>`，Android 的 `onShowFileChooser`）

交互设计：

- 首次请求时弹出底部面板，显示完整 origin、请求类型、允许一次 / 始终允许 / 阻止。
- 默认拒绝；关闭面板等同拒绝。
- “始终允许”写入 `permissions` 表，按 `origin + permission` 唯一；隐私设置页提供按站点撤销。
- 权限状态变化要能被页面感知：允许后重新触发请求，而不是让页面一直挂起。

平台实现：

- **CEF**：需要在原生插件中接 `CefPermissionHandler`（媒体、地理位置、通知）和文件对话框回调。和下载一样，属于同一个上游补丁包；建议把“下载 + 权限 + 请求上下文”作为一个 CEF 绑定 PR 交付，减少反复升级。
- **Android**：自定义 `WebChromeClient` 处理 `onPermissionRequest`、`onGeolocationPermissionsShowPrompt`、`onShowFileChooser`。`onPermissionRequest` 必须在内层 WebView 上设置，不能只在外层 Activity 请求。

### 证书错误

- CEF：`CefRequestHandler::OnCertificateError` 回调；把错误码、域名、证书主题传给 Lynx，显示内部错误页。
- Android：`WebViewClient.onReceivedSslError`，默认 `handler.cancel()`；不要提供“继续访问”作为默认按钮。
- 错误页提供“返回上一页”“复制错误详情”，以及一个需要二次确认的“仍要继续（不推荐）”，并明确说明风险。0.2 可以先不做继续访问，保持默认拒绝。

### 验收

- 本地 HTTPS 自签名页面触发证书错误页，显示域名和错误码，无法在一步点击内绕过。
- 摄像头/麦克风请求在 Windows 与 Android 都能弹出提示；拒绝后页面收到 `NotAllowedError`。
- 选择“始终允许”后刷新页面不再提示；在设置中撤销后再次提示。
- 文件选择在 Android 上能选到 Downloads 和图片库中的文件。

## 工作流 C：隐私标签

0.1 的 `WindowState.private` 只影响历史/会话。真正的隐私浏览至少要求 Cookie、缓存、LocalStorage 不与普通会话共享。

三种方案：

| 方案 | 隔离程度 | 代价 | 建议 |
| --- | --- | --- | --- |
| CEF 独立 request context / cache path | 完整 | 需要原生绑定扩展 | 目标方案 |
| 隐私模式单独进程 | 完整 | 启动成本高，跨进程通信复杂 | 不推荐 |
| 关闭时清 Cookie/缓存 | 部分，且会误伤普通会话 | 实现简单但语义错误 | 不采用 |

因此，**完整的隐私标签依赖 CEF 请求上下文接口**。0.2 的处理建议：

- 如果上游补丁包含 request context，就实现每个隐私窗口一个独立 context，关闭窗口时销毁；验收“普通标签已登录，隐私标签未登录；关闭隐私标签后普通会话仍在”。
- 如果补丁不包含，0.2 不伪装成完整隐私浏览：把 UI 文案改成“不记录历史”，并在设置页说明 Cookie 仍共享；完整隔离排到 0.3。不要在 0.2 里用“关闭时清 Cookie”糊弄，这会破坏普通标签的登录状态。

## 工作流 D：Android 端对齐

### 文件选择与导入导出

- 自定义 `WebChromeClient.onShowFileChooser`，用 `ActivityResultContracts.OpenDocument` 支持单选/多选，回传 `Uri[]` 给 WebView。
- 书签 HTML 导入/导出走 SAF：`ACTION_OPEN_DOCUMENT` / `ACTION_CREATE_DOCUMENT`，复用桌面端的 HTML 解析/生成逻辑，放在 `packages/core` 或 `packages/storage` 的纯函数层。
- 油猴脚本文件导入同样走 SAF；脚本安装确认页复用现有风险提示。

### 下载

见工作流 A。Android 需要额外处理通知权限（Android 13+ `POST_NOTIFICATIONS`），以及下载完成后 `FileProvider` 打开文件的 MIME/权限。

### 版本与签名

`apps/android/android/app/build.gradle.kts` 当前 `versionName = "1.0"`，而产品版本是 `0.1.0`；`versionCode = 1` 也不适合持续升级。0.2 应统一从根 `package.json` 或 `gradle.properties` 注入版本，`versionCode` 用单调递增的构建号。发布构建使用独立 keystore，密钥放 CI secret，不提交仓库。

### 状态快照可靠性

在 DuckDB 落地前，先让 JSON 快照变可靠：

- 写入临时文件 + `fsync` + 原子 rename，避免半写损坏。
- 顶层加 `schemaVersion`，加载时执行显式迁移；未知版本拒绝覆盖并备份原文件。
- 保留最近一份 `.bak`；启动时主文件解析失败自动回退并提示。
- 限制单文件大小，避免脚本值/历史无限增长。

这些改动不依赖 DuckDB，能直接降低 0.2 的数据风险。

## 工作流 E：油猴脚本增强

现状：`parseMetadata` 已解析 `@require`、`@resource`、`@run-at`；`buildInjection` 只拼接脚本源码，没有加载依赖，也没有按 `stage` 区分。`GM_download` 在 UI 侧未接通。

0.2 建议：

1. **`@require`**：安装或首次运行时抓取 URL，缓存到 `userscript_resources`；注入时按声明顺序放在脚本之前。设置大小上限（例如单文件 2 MB、单脚本 5 MB）、超时和失败提示。
2. **`@resource`**：同样缓存，补齐 `GM_getResourceText` / `GM_getResourceURL` 的 shim；资源名大小写敏感，和 Tampermonkey 保持一致。
3. **`@run-at`**：`document-end` / `document-idle` 可以在现有 `bindload` 之后用 `setTimeout` 区分；真正的 `document-start` 仍需要引擎在导航开始时注入，0.2 先明确标注“尽力提前”，不要宣称严格 document-start。
4. **`GM_download`**：接到工作流 A 的下载管理器；返回值/回调语义按 Tampermonkey 文档实现，失败时给脚本明确的 error。
5. **测试**：三个脚本样例覆盖 require、resource、GM_download；纯函数测试放 `packages/userscript`，注入集成测试用 `test-pages`。

## 工作流 F：Android DuckDB 的决策

结论：**0.2 不做，0.3 再评估**。理由不是“难”，而是当前收益/成本不划算：

- DuckDB 2.0.1 的 GitHub Release 资产没有 Android 包；官方 CI 的 `Android.yml` 会用 NDK 构建 `libduckdb-android_armeabi-v7a.zip` 和 `arm64-v8a.zip`，但没有作为公开 Release 资产发布。要稳定使用，需要自己维护 NDK 构建、缓存和 ABI 打包。
- Maven Central 上的 `org.duckdb:duckdb_jdbc` 不是 Android 可用的原生库路径；现有社区方案多为个人 fork，不能作为长期依赖。
- 包体积会明显增加。当前 debug APK 已经约 76 MB，再加入两个 ABI 的 DuckDB 动态库，安装包和启动成本都会上升。
- 0.1 的 JSON 快照已经能覆盖单机状态；先做原子写入、版本迁移和备份，能解决更紧迫的数据安全问题。

0.3 的触发条件：DuckDB 官方发布 Android Release 资产，或项目愿意维护一条独立的 NDK 构建流水线并把包体积纳入预算。迁移时保留一次性 JSON → DuckDB 导入，不做双写。

## 工作流 G：发布工程

0.2 要把“能构建”变成“能重复构建、能验证、能升级”。

- **CI**：GitHub Actions 在 push/PR 上跑 `bun install --frozen-lockfile`、`bun run check`、`bun run docs:build`；缓存 Bun 和 Gradle。
- **版本一致性**：根 `package.json`、`apps/desktop/package.json`、Android `versionName`/`versionCode`、Release tag 使用同一个版本源；加一个脚本校验。
- **Windows 签名**：有证书时用 `signtool` 签安装包和 exe；没有证书时在 Release 说明中明确“unsigned”，不要假装已签名。
- **Android 签名**：release keystore 放 CI secret，产出 `app-release.apk`；debug APK 继续作为开发产物，但不作为正式下载。
- **校验和**：发布流程生成 `SHA256SUMS.txt`，Release 说明里给出验证命令。
- **更新检查**：0.2 先做“检查 GitHub Releases 是否有新版本 + 打开下载页”，不做静默安装。静默更新要等代码签名和回滚策略就绪。
- **文档**：README、README_zh、VitePress 和 CHANGELOG 在同一 PR 更新；文档站通过 GitHub Pages 自动部署。

## 工作流 H：多窗口（P2）

现有 `WindowState` 和 `windows` 表已经为多窗口留了模型，但 UI 仍按单窗口运行。0.2 不建议做，原因是：

- 桌面端需要 Lynxtron 多 `BrowserWindow` 的生命周期、会话恢复和 CEF 视图迁移；Android 端 “多窗口”更接近多任务/分屏，语义不同。
- 它会和隐私窗口的 request context、下载管理器、权限来源绑定，最好在这些基础能力稳定后再做。

如果要做，先做“标签页溢出管理/标签搜索”，不要直接做窗口撕裂；前者成本低，能先验证用户需求。

## 里程碑

| 阶段 | 时间 | 交付 |
| --- | --- | --- |
| M0 决策 | 第 1 周 | CEF 绑定 spike 结论；确定上游 PR 还是 fork；版本/CI 基线；JSON 原子写入 |
| M1 下载 | 第 2–4 周 | 统一下载模型、桌面 CEF 下载、Android DownloadManager、下载页交互 |
| M2 权限 | 第 4–6 周 | 权限提示、持久化、撤销；证书错误页；Android 文件选择 |

## 0.2.0 验收清单

- [ ] Windows 与 Android 都能完成一次真实文件下载，进度、暂停/继续/取消、重启恢复正确。
- [ ] 摄像头、麦克风、定位、通知、文件选择五类权限有提示、有持久化、可撤销。
- [ ] 自签名 HTTPS 页面显示证书错误页，默认不能继续。

## 风险与开放问题

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| CEF 上游不接受下载/权限补丁 | 桌面端关键路径阻塞 | M0 spike；准备 fork；保留拦截降级 |
| Android WebView 版本碎片化 | 权限/文件选择行为不一致 | API 24、30、34、35 真机/模拟器矩阵 |
| 隐私隔离语义不完整 | 用户信任受损 | 未实现就不使用“隐私浏览”文案；0.3 补全 |
| DuckDB Android 包体积/构建 | 安装包膨胀 | 0.2 不做；0.3 用官方资产或独立流水线 |
| Windows 无代码签名证书 | SmartScreen 警告 | Release 明确标注；有证书后再做自动更新 |
| JSON 快照损坏 | 数据丢失 | 原子写入 + 备份 + 版本迁移 |
| 范围膨胀 | 0.2 延期 | P0/P1 冻结；多窗口、DuckDB、静默更新移出 |

需要维护者拍板的问题：

1. Windows 代码签名证书和 Android release keystore 是否在 0.2 前准备好？如果没有，0.2 是否接受继续发布 unsigned/debug 构建？
2. 隐私标签在 0.2 必须做到 Cookie 隔离，还是可以先改成“不记录历史”的诚实文案？
3. CEF 补丁优先走上游 PR，还是允许维护 fork？这决定 M1 的时间线。
4. Android 最低版本是否维持 API 24？如果要支持文件选择/下载的现代行为，是否考虑提高到 API 26 或 28？
5. 0.2 是否允许为了下载/权限引入新的原生依赖或显著增加安装包体积？

这些问题不需要现在全部回答，但第 1 和第 3 个必须在 M0 结束前有结论，否则 0.2 的关键路径无法排序。
